A NOTE BEFORE YOU START
-----------------------

Both of these have now failed twice, and both times I gave you a fix
based on a diagnosis that turned out to be wrong. So this round is
built differently.

Neither fix is a guess this time. Both have been demonstrated on this
machine: the app is driven from another program, and the tray responds
to a keypress exactly the way the shell delivers one, and a synthetic
mouse movement is correctly identified as the mouse.

What I still cannot check from here is whether the icon you actually
reach with Windows+B is the one this app owns, and whether a real
trackpad behaves like a synthetic one. So the app now writes a line to
the log every time the tray icon is touched, and can be asked to
explain each decision it makes about the keyboard and the mouse.

That means if something still fails, the log will say why, and there
will be no fourth round of guessing.


WHAT CHANGED, AND WHY
---------------------

1. The tray. Version 4, last round's fix, was accepted all along - the
   log now proves it - so that was never the whole story.

   The real fault: Windows can deliver a message to a program in two
   ways, and only one of them was being listened to. The hotkey and the
   timer are "posted", which is the way the app was watching for. The
   tray callback is "sent", which goes somewhere else entirely and was
   being thrown away. Every click and every keypress on the icon, since
   the tray was first built, discarded before anything looked at it.

2. The trackpad. Both previous attempts worked out whether input came
   from the mouse by watching where the pointer was. That was the wrong
   tool: a trackpad clearly produces input that the pointer position
   does not account for, and no amount of refining it was going to
   find that.

   The mouse now tells us directly. Windows will report mouse activity
   to a program that asks, so the app asks. It registers for the mouse
   only, and never reads what the events contain - the time is all it
   wants - so it still cannot see a keystroke, which was the reason for
   avoiding this kind of thing in the first place.

3. The icon is now removed when the app is killed, not just when it
   exits properly. Closing the console window used to leave the icon
   behind, still listed and still read out, but attached to a program
   that no longer exists. That may well be why the name has been read
   twice over both times - one live icon and one corpse. It would also
   explain Enter doing nothing, since pressing a dead icon cannot do
   anything.

4. The on-tone now starts after an eighth of a second rather than a
   quarter, as you suggested.
